# M5 MCP Server (AI Access) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Any MCP-capable AI app (Claude, ChatGPT, Cursor, Claude Code…) can connect to the app, but only after the owner signs in and approves it. It can then read and change the owner's goals through the same domain actions the UI uses, every change it makes shows in History as "<App> via MCP" and can be undone, and the owner can see and revoke connected apps in Settings.

**Architecture:**
- **Authorization server:** the app itself, through Better Auth.
  - `jwt()` for signing keys and `/jwks`.
  - `@better-auth/mcp`'s `mcp()`, which *is* the OAuth provider for MCP: authorization code + S256 PKCE, refresh tokens, consent, and RFC 9728/8414 metadata.
  - `@better-auth/cimd`'s `cimd()` for Client ID Metadata Documents, which the 2026-07-28 MCP spec prefers.
  - Dynamic client registration stays on as a fallback, for clients still on the 2025 flow.
- **Resource server:** `/api/mcp` is a stateless MCP SDK v2 handler (`createMcpHandler` from `@modelcontextprotocol/server`), wrapped in two layers:
  1. Better Auth's `requireMcpAuth`, which checks the JWT's signature, audience and expiry.
  2. Our own `authorizeMcp`, which checks the owner, the client's live consent (so revoking is immediate even though JWTs can't be revoked) and the rate limit, and sets the actor `mcp:<client name>`.
- **Tools:** one table in `src/server/mcp/tools.ts` maps each spec §7.2 tool to an existing domain action. It reuses that action's Zod input schema and adds a model-facing description and a one-line summary. No domain logic lives in the MCP layer.

**Tech Stack:** as M4. **New:** `@better-auth/mcp`, `@better-auth/cimd`, `@modelcontextprotocol/server` 2.x, and dev `@modelcontextprotocol/client` 2.x (in-process adapter tests and the E2E). Versions are pinned by the lockfile at install. `@better-auth/oauth-provider` comes in as `@better-auth/mcp`'s dependency.

**Spec:**
- Technical design: `docs/superpowers/specs/2026-10-22-life-goals-app-technical-design.md` §7 (endpoint, tools, authorization flow, risk/fallback), §6.1–6.2 (owner-only, rate limiting), §4 (`oauth_clients_seen`), §9 (adapter tests, MCP smoke).
- Product design: `docs/superpowers/specs/2026-10-21-life-goals-app-design.md`, "Decided: AI access (MCP)", "Decided: safety net".
- Roadmap: `docs/ROADMAP.md` § M5.

## Global Constraints

- **M2–M4's Global Constraints hold**, including:
  - The domain boundary rule: `src/server/mcp/**` may import `domain`, but `domain` never imports `mcp`.
  - The ≥90% line gate on `src/lib` and `src/server/domain`.
  - Owner check first in every adapter.
- **Only the owner can connect (spec):**
  - Tokens are issued only after the owner's own sign-in and consent.
  - Every MCP request re-checks that the token's `sub` is a user whose email is `OWNER_EMAIL`, the same rule as `checkOwner`.
  - A signed-in non-owner reaching `/oauth/consent` gets 404, like every page.
- **Actor (§7.3):** `mcp:<client name>`. The client name comes from the registered client (DCR `client_name`, or the CIMD document's `client_name`), else its `client_id` host, else "AI app".
- **Endpoint (§7.1):** `POST /api/mcp`, stateless. `GET`/`DELETE` → 405.
- **Unauthenticated (§7.3 step 1):** 401 with `WWW-Authenticate` pointing at `/.well-known/oauth-protected-resource…` (RFC 9728).
- **Public paths (proxy):**
  - `/api/mcp`: it authenticates by bearer token, not by cookie.
  - `/.well-known/` (prefix).
  - `/oauth/consent` stays owner-only, so the proxy sends a signed-out visitor to `/login?next=…` and they return to consent after signing in.
- **Consent copy (§7.3):** "**{client name}** wants to read and change your goals", with buttons `Approve` and `Deny`.
- **Responses (§7.2):** compact JSON plus a one-line human summary.
- **Errors:** a `DomainError` becomes an MCP tool error (`isError: true`) whose text is M2's `messageFor(code, details)`. Nothing else leaks; unexpected errors are generic.
- **Rate limit (§6.2):** `/api/mcp` allows 120 requests per minute per token subject + client. Over the limit → 429 with `Retry-After`. `/login`'s sign-in endpoints are already limited by Better Auth's `rateLimit` in production (M0); Task 5 pins that with a test.
- **Settings copy:**
  - Section "Connected AI apps".
  - Each row shows the app name and "Last used {timeAgo}", plus a `Revoke` button.
  - Empty: "No AI apps connected. Add this app's MCP URL in your AI app: {origin}/api/mcp".

## Review Focus

1. **A revoked app's still-valid JWT** (minutes left on it) must be refused on its next request, not served until expiry. Test: Task 2.
2. **A token minted for the owner but replayed against a preview or another deployment** (wrong audience/resource) is refused. Test: Task 2, via `requireMcpAuth`'s `resource` option.
3. **A tool call with bad input from a model** (wrong id format, missing fields, an unknown status) returns a readable tool error, not a 500 or a stack trace. Test: Task 3.
4. **`create_tasks` with 15 items is one batch:** a single History row "Claude via MCP · Added 15 tasks", undone in one step. Test: Task 3.
5. **The consent page reached directly** (no signed OAuth query, or a tampered one) shows "This link has expired or is invalid", never an Approve button. Test: Task 4.

  4. Upsert `oauth_clients_seen`, setting `last_used_at = now`.
- The route uses the caller's `ownerId` and `actor` for every action: `runAction({ db, ownerId, actor })`.
